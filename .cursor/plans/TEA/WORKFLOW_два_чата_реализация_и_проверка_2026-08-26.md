# Workflow: два чата Cursor — реализация и проверка

**Дата:** 2026-08-26  
**Назначение:** как вести пошаговую реализацию по плану в одном чате (тяжёлая модель) и проверку каждого шага в другом чате (лёгкая модель).

Два агента **не видят** переписку друг друга. Общий контекст — только файлы и git.

---

## 1) Роли и режимы

| Чат | Модель | Режим Cursor | Права |
|-----|--------|--------------|--------|
| **Реализация** | тяжёлая | **Agent** | пишет код, правит файлы, **один шаг плана** |
| **Проверка** | лёгкая | **Ask** (только чтение) | смотрит diff + план, **ничего не меняет** |

Ask для проверки обязателен: лёгкая модель в Agent начнёт «чинить» код и разъедется с реализатором.

Не гонять оба чата по одним файлам одновременно. Цикл строго последовательный:

```
шаг → handoff → ревью → правки (если надо) → следующий шаг
```

---

## 2) Общие артефакты (источник правды)

В папке конкретного плана:

```
.cursor/plans/<задача>/
  PLAN.md              ← нумерованные шаги + чекбоксы
  STATUS.md            ← текущий шаг, вердикт ревью
  handoff/step-NN.md   ← пишет исполнитель после шага
  review/step-NN.md    ← пишет ревьюер (опционально) или копируется из чата
```

Реализатор после шага **пишет handoff на диск**. В чате проверки достаточно `@` на `PLAN.md`, `STATUS.md` и `handoff/step-NN.md` — копировать простыни из чата не нужно.

Вы — диспетчер. Не просить реализатора «сам вызови ревью»: он не видит второй чат.

---

## 3) Шаблон STATUS.md

Одна страница, которую читают оба чата:

```markdown
# STATUS
- Задача: #NNNN
- План: PLAN.md
- Текущий шаг: 3 — «…название…»
- Состояние: waiting-review | rework | passed
- Diff scope: git diff (unstaged + staged), файлы из шага 3
- Последний handoff: handoff/step-03.md
- Последнее ревью: review/step-03.md
```

Состояния:

| Значение | Смысл |
|----------|--------|
| `waiting-review` | шаг сделан, ждём проверку |
| `rework` | ревью FAIL, исполнитель правит блокеры |
| `passed` | шаг принят, можно следующий |

---

## 4) Как писать шаги плана

Каждый шаг — контракт, а не пожелание. Иначе лёгкая модель будет спорить с воздухом.

```markdown
## Шаг 3. Добавить валидацию X
**Цель:** …
**Делать:** …
**Не делать:** шаг 4, рефакторинг рядом, новые файлы вне списка
**Ожидаемые файлы:** `path/a.cs`, `path/b.cs`
**Критерий готовности:**
- [ ] …
- [ ] нет изменений вне ожидаемых файлов (кроме .meta от Unity)
**Как проверить:** git diff + …
```

Чем жёстче границы шага, тем полезнее лёгкий ревьюер.

Как отмечать прогресс (как в остальных планах TEA):

- `[ ]` — не начато
- `[~]` — в работе
- `[x]` — завершено

Сначала закрываются подзадачи, затем шаг.

---

## 5) Цикл на один шаг

```
Вы → Реализация: «делай текущий шаг»
     ↓
Реализация пишет код + handoff + STATUS = waiting-review
     ↓
Вы → Проверка: «проверь шаг N»  (@PLAN @STATUS @handoff)
     ↓
  FAIL → Реализация: «правь по review, скоуп не расширять»
         STATUS = rework
  PASS → Вы / реализатор: «шаг принят, следующий»
         STATUS = passed, затем новый текущий шаг
```

Короткие команды после стартовых промптов:

**Реализатору**

- `Делай текущий шаг.`
- `Ревью FAIL, вот review/step-03.md — правь только блокеры.`
- `Шаг принят. Переходи к следующему.`

**Ревьюеру**

- `Проверь шаг из STATUS.md. Handoff: @handoff/step-03.md`

---

## 6) Стартовый промпт — чат РЕАЛИЗАЦИИ

Вставить первым сообщением. Прикрепить `@PLAN.md` и `@STATUS.md`.

```text
Ты — исполнитель. Режим: Agent. Работаешь строго по плану.

Источник правды:
- план: @PLAN.md
- статус: @STATUS.md

Правила:
1. Делай ТОЛЬКО текущий шаг из STATUS.md. Следующие шаги не начинай.
2. Не выходи за «Ожидаемые файлы» и «Не делать» этого шага.
3. Не коммить и не пушь, пока я явно не попрошу.
4. После шага не предлагай «сразу сделать шаг N+1».
5. В конце шага:
   - обнови чекбоксы шага в PLAN.md
   - обнови STATUS.md: состояние = waiting-review
   - запиши handoff/step-NN.md по шаблону ниже
   - в чат выведи короткий итог и путь к handoff

Шаблон handoff/step-NN.md:
# Handoff — шаг N
- Что сделано (3–7 пунктов)
- Файлы (созданы / изменены / удалены)
- Что сознательно НЕ сделано (вне шага)
- Как проверить (команды / где смотреть)
- Риски / сомнения
- Готово к ревью: да

Жди вердикт ревью. Если пришлю FAIL — правь только пункты из review/step-NN.md, без расширения скоупа.
```

## 7) Шаблон handoff/step-NN.md

```markdown
# Handoff — шаг N

- Что сделано:
  - …
- Файлы:
  - созданы: …
  - изменены: …
  - удалены: …
- Что сознательно НЕ сделано (вне шага):
  - …
- Как проверить:
  - …
- Риски / сомнения:
  - …
- Готово к ревью: да
```

## 8) Стартовый промпт — чат ПРОВЕРКИ

Чат в **Ask**. Первое сообщение. Прикрепить `@PLAN.md`, `@STATUS.md`, `@handoff/step-NN.md`.

```text
Ты — ревьюер шага плана, не соавтор. Режим: Ask. Код не меняй, файлы не пиши
(кроме review/step-NN.md — только если я явно разрешу запись).

Контекст:
- план: @PLAN.md
- статус: @STATUS.md
- handoff исполнителя: @handoff/step-NN.md

Сначала сам сними факт:
1. git status / git diff / git diff --cached
2. список файлов из handoff vs реальный diff
3. критерий готовности ТЕКУЩЕГО шага в PLAN.md

Проверяй только текущий шаг. Не ревьюй будущие шаги и не предлагай «улучшения наперёд».

Ищи:
- ошибки, явные баги, сломанные контракты
- расхождение с целью/критериями шага
- scope creep (файлы и правки вне шага)
- дыры относительно критерия готовности
- нарушение правил репозитория (Unity .meta руками, MpGenerated, коммиты без refs #)

Не придирайся к стилю, если это не ломает конвенции проекта.
Лёгкая модель: если не уверен — помечай «вопрос», не выдавай за блокер.

Вердикт — строго один:
- PASS — шаг закрыт, можно следующий
- PASS_WITH_NOTES — можно идти дальше, заметки не блокируют
- FAIL — нельзя следующий шаг; список блокеров

Формат ответа:
## Вердикт: PASS | PASS_WITH_NOTES | FAIL
## Соответствие плану
| Критерий шага | Статус | Комментарий |
## Scope
- лишнее / недостающее
## Замечания
### Блокеры
### Некритично
### Вопросы
## Итог для исполнителя
- что править (если FAIL), копируемым списком
```

---

## 9) Кто пишет review/step-NN.md и STATUS.md

Предпочтительно:

- ревьюер отвечает **только в чат**;
- статус обновляет **исполнитель** после вашей команды «принято» / «на правки».

Так лёгкая модель меньше портит артефакты.

Если ревьюеру всё же разрешить запись (тогда не Ask, а Agent с жёстким запретом трогать код):

```text
Запиши отчёт в review/step-NN.md. Другие файлы не трогай.
STATUS.md: поставь passed или rework.
```

---

## 10) Чего ждать от лёгкой модели

**Хорошо ловит**

- не тот файл;
- шаг N+1 влез в шаг N;
- критерий готовности не закрыт;
- забытый null-check;
- расхождение handoff и реального diff.

**Слабо ловит**

- тонкую архитектуру;
- гонки;
- скрытые регрессии в SharedLogic / доменной логике.

Поэтому в промпте проверки: **сначала факты (diff vs план), потом мнение**. Блокером считать только то, что привязано к критерию шага или явной ошибке.

Тяжёлое ревью перед сдачей задачи (self-review / MR review) — **другой слой**, не замена пошаговой проверке.

---

## 11) Как закрепить, чтобы не копировать промпты каждый раз

По возрастанию удобства:

1. **Два чата + стартовые промпты** из §6 и §8 — хватит на первую задачу.
2. **Custom Mode** в Cursor: «Implementer» (Agent) и «Reviewer» (Ask) с этими правилами в instructions.
3. **Два skill’а** в `.cursor/skills/`: `/implement-step` и `/review-step`, `disable-model-invocation: true` — вызываете слэшем, модель сама не путает роли.

Правила в `.cursor/rules` с `alwaysApply: true` для этого **не** ставить: оба чата начнут вести себя одинаково.

---

## 12) Чеклист запуска пары чатов

- [ ] План с машиночитаемыми шагами (цель / делать / не делать / файлы / критерий)
- [ ] Есть `STATUS.md` с текущим шагом
- [ ] Чат реализации: Agent, тяжёлая модель, промпт §6, `@PLAN` `@STATUS`
- [ ] Чат проверки: Ask, лёгкая модель, промпт §8, `@PLAN` `@STATUS`
- [ ] После каждого шага есть `handoff/step-NN.md`
- [ ] Ревью смотрит только текущий шаг и реальный `git diff`
- [ ] FAIL → правки только по списку блокеров, без расширения скоупа
- [ ] PASS → следующий шаг, не раньше
