# План реализации прототипа боевого режима

Дата: 2026-08-10  
Область: `Modules.RPG` + `Modules.Windows` + интеграция с `Definitions/State/Restrictions/Dices`

## 1. Цель прототипа

Собрать вертикальный срез боевого режима, который работает от adventure-выбора до завершения боя и возврата в сцену:

- запуск боя из `ChoiceActionType.StartCombat` (или временного аналога);
- пошаговый цикл «сторона игрока -> сторона противника»;
- базовые боевые действия (`Strike`, `RaiseShield`, 1-2 простых utility-опции);
- базовый UI-экран боя (лог, панель действий, список целей, состояние бойцов);
- запись итогов в `State` (HP/статусы у героев) и корректный выход обратно в adventure-flow.

Прототип не пытается закрыть весь PF2e-слой, а фиксирует минимально жизнеспособный runtime-контур.

## 2. Границы прототипа (In / Out)

### In Scope

- session-модель боя на 2 стороны;
- AP-экономика хода стороны (`ActionsPerTurn`);
- таргетинг `Self`, `EnemySingle`, `EnemyAll`;
- hit-check и damage-roll на базе `Dices` + `WeaponProxy` + MAP;
- базовая доступность действий через `Restrictions`;
- простой AI противника (эвристика «первое валидное действие + случайная цель»);
- отдельное окно боя с минимальным UX.

### Out of Scope (для следующего этапа)

- реакция/AoO, сложные триггеры, инициатива по каждому существу;
- продвинутые анимации и VFX;
- полноценный loot/exp/economy-проход после боя;
- сложный encounter-builder в TEA (достаточно простого контракта на старте).

## 3. Архитектура прототипа

## 3.1 Runtime-слой боя

Добавить изолированный слой (условно `Combat` внутри `Modules.RPG`):

- `BattleSession` — состояние боя в рантайме (стороны, текущий ход, оставшиеся действия, counters, лог событий);
- `BattleSideRuntimeData` — бойцы стороны, side-id, AI/manual-флаг;
- `BattleActorRuntimeData` — ссылка на `CharacterStateData`, жив/мертв, временные runtime-флаги;
- `BattleActionResolver` — применение `BattleActionDef` (валидация -> броски -> эффекты -> лог);
- `BattleTurnController` — start/end turn, списание AP, переключение стороны;
- `BattleResult` — исход боя (`Victory/Defeat/Retreat`) + изменения для переноса в state.

Ключевая идея: `BattleSession` хранит только runtime-временные данные, а состояние персонажей мутируется через существующие state-action/операторы.

## 3.2 Контракт входа в бой

Добавить минимальный контракт запуска:

- `StartCombat` action из adventure-choice;
- payload должен содержать id encounter и/или список `CreatureDef` для противников;
- party берётся из `StateData.Characters.ActivePartyCharacterIds`.

Для MVP допустим «временный простой encounter-контракт» (1 JSON-коллекция с enemy-составом и мета-параметрами).

## 3.3 Контракт выхода из боя

После завершения:

- если `Victory`: применить итоговые HP/статусы героев и выполнить `OnWin`-actions;
- если `Defeat`: применить итоговые HP/статусы (или safe-minimum политику) и выполнить `OnLose`-actions;
- вернуть UI в adventure runtime и вызвать refresh content/choices.

## 4. UI-окно боя (прототип)

Добавить отдельное окно, например `BattleWindow`:

- верх: текущая сторона, AP, номер раунда;
- левый блок: список союзников (HP, ключевые статусы);
- правый блок: список противников (HP, ключевые статусы);
- низ: кнопки доступных действий выбранного актёра;
- центр/низ: combat-log последних событий.

MVP-поведение:

- выбор актёра своей стороны;
- выбор действия;
- выбор цели (если требуется);
- кнопка `End Turn`;
- блокировка инпута, когда ход AI.

Требования UX для MVP:

- все действия UI должны быть обратимы на шаге выбора (до подтверждения применения);
- при ошибке валидации показывать user-friendly сообщение (не технический exception);
- после боя окно закрывается гарантированно, даже при частичной ошибке пост-обработки (с логом ошибки).

## 5. Этапы реализации

## Этап 1. Контракты и данные

1. Уточнить/добавить `ChoiceActionType.StartCombat` в актуальный enum/фабрику.
2. Ввести DTO для запуска боя (`StartCombatParams`, `EncounterRef`).
3. Добавить минимальные encounter-дефы (состав врагов, опциональные `OnWin/OnLose` actions).
4. Зафиксировать ссылочную схему id (encounter id, creature id, battle-rule id).

Результат:

- из adventure-контента можно декларативно вызвать бой.

## Этап 2. Core-логика боя

1. Реализовать `BattleSession` + `BattleTurnController`.
2. Реализовать подготовку бойцов:
   - герои: `CloneForBattle`;
   - враги: `CreatureCombatantFactory.CreateFromCreature` с отрицательными id.
3. Реализовать победу/поражение (бой окончен, когда одна сторона без живых бойцов).
4. Реализовать `MapCounterScope` MVP (рекомендовано `PerActor`).

Результат:

- бой симулируется до конца без UI.

## Этап 3. Resolver боевых действий

1. Реализовать `BattleActionResolver`:
   - проверка доступности (`Restrictions`, AP, таргет);
   - MAP-логика из `BattleRuleDef`;
   - hit-check и damage/heal;
   - базовые эффекты (`Damage`, `Heal`, `AddStatus`, `RemoveStatus`).
2. Добавить лог-события (`BattleLogEvent`) для UI.
3. Подключить базовый AI хода соперника.

Результат:

- battle-actions реально влияют на HP/статусы и дают воспроизводимый combat-log.

## Этап 4. Окно и VM-слой

1. Создать `BattleWindow` и `BattleWindowViewModel`.
2. Подключить подписку на события session/log.
3. Реализовать interaction-flow:
   - select actor -> select action -> select target -> confirm.
4. Реализовать состояние «ход AI» и блокировку пользовательских кнопок.

Результат:

- бой полностью проходим через UI.

## Этап 5. Интеграция с adventure-loop

1. В executor для `StartCombat`:
   - открыть окно боя;
   - дождаться результата;
   - применить `OnWin/OnLose` choice-actions через существующую фабрику executors.
2. Обновить runtime refresh после боя (`ChangedContent`/`ChangedChoices` при необходимости).
3. Зафиксировать policy записи итогов боя в state.

Результат:

- от клика выбора в сцене можно пройти бой и вернуться в сценарий.

## Этап 6. Тесты и стабилизация

1. Unit-тесты:
   - MAP и расчёт hit-check;
   - завершение боя и определение победителя;
   - ограничения доступности действий;
   - перенос результата в state.
2. Интеграционные тесты:
   - `StartCombat` из adventure сцены;
   - `Victory -> return to scene`;
   - `Defeat -> return to scene`.
3. Debug tooling:
   - принудительный seed;
   - опциональный «быстрый автопроход» для QA.

Результат:

- прототип воспроизводим и пригоден для контентной обкатки.

## 6. Риски и меры

- Риск: разрыв между battle-session и state-actions.  
  Мера: единая точка commit результатов в конце боя + явный контракт `BattleResult`.

- Риск: перегрузка UI сложными механиками.  
  Мера: жёсткий MVP-набор действий и таргетов, без расширений до стабилизации.

- Риск: контентные ошибки в encounter JSON.  
  Мера: валидатор ссылок (`creature id`, `action id`, `onWin/onLose`) до старта боя.

- Риск: зависание flow при ошибке окна/экзекьютора.  
  Мера: fail-safe завершение боя с возвратом в adventure и логированием причины.

## 7. Definition of Done (MVP)

- Бой запускается из приключения одним choice-action.
- Игрок может завершить бой через UI без ручных консольных команд.
- Работают минимум: атака, лечение/баф, завершение хода, простой AI соперника.
- Победа/поражение корректно возвращают в adventure и применяют соответствующие actions.
- HP и ключевые статусы героев корректно переносятся в state.
- Ключевые сценарии покрыты тестами и не падают на базовом контенте.

## 8. Практический порядок на 2 спринта

Спринт 1:

- Этап 1 + Этап 2 + skeleton Этапа 3;
- минимальный headless бой (без финального UI), доступный через debug entry.

Спринт 2:

- завершение Этапа 3;
- Этап 4 + Этап 5;
- Этап 6 (тесты/стабилизация) и первый контентный прогон на 1-2 мини-приключениях.

## 9. Следующий шаг после MVP

После закрепления прототипа:

- расширить encounter-контракт (награды, волны, модификаторы локации);
- добавить более богатые боевые эффекты и реакции;
- провести UX-проход окна (подсказки, прогноз урона, индикаторы шансов).
